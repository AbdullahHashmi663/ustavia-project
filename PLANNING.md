## 3. Business context that shapes the plan

- **One MVP, one codebase, hard deadline.** The docx is dated 7 Sep 2026 with a 20 Dec 2026 launch target — roughly 14 weeks from today. The two 40+ page UX specs describe a much larger, two-sided consumer marketplace (think a mature ride-hailing app) than the docx's leaner MVP brief. They are aspirational reference material, not a literal must-build-every-screen checklist for this deadline.
- **Existing architecture already made a scoping call**, documented in `ARCHITECTURE.md` and `CHANGELOG.md`:
  - **One React Native app, role locked at signup** (Customer *or* Mazdoor, immutable for MVP) — not two separate apps as the PDFs' onboarding flows (e.g. Worker PDF's "Worker vs Customer Selection Screen") imply. Dual-role is explicitly deferred (`CHANGELOG.md` → Unreleased → Planned).
  - **Job flow is post-and-negotiate, not browse-and-hire-a-specific-worker.** The customer posts a job (area + distance shown to nearby Mazdoors, no pinpoint location); Mazdoors discover it, open a chat, negotiate price/time, and a confirmation form locks it in. The Customer PDF's Home screen (live worker map, "Hire Now" on a specific worker's profile, bid-comparison dashboard) assumes the opposite model. **This is the single biggest reconciliation point in this plan — see §4.**
  - The job state machine (`posted → negotiating → confirmed → in_progress → completed → paid`, with a `disputed` branch), the 4‑digit entry PIN, server-side chat redaction, mid-job Material Quotes, platform cut %, and FBR withholding % are **already implemented** in `packages/shared` and `apps/mobile/src/store/jobs.ts`. This is real, working domain logic — the plan should style and complete the screens around it, not replace it.

## 4. Reconciling the two UX specs with what's actually built

Rather than transplant the PDFs' full browse/map/hire-a-worker information architecture (a scope change that would blow the Dec 20 date), this plan treats them as a **pattern library**: screen layouts, copy tone, state handling (loading/empty/error), icon placement, and micro-interactions to borrow for the screens Ustavia actually has, while keeping the post-and-negotiate model. Concretely:

- **Adopt directly** (same model, just needs building/styling): auth & OTP flow, CNIC/KYC verification states, chat screen, live job-status timeline, SOS activation/active screens, wallet/earnings screens, withdrawal flow, ratings & review, dispute flow, profile/settings, notification center.
- **Adapt, not copy** (different model — reinterpret the *pattern*, not the *flow*): the Customer PDF's live worker map and "Book Now on this worker's profile" become, in Ustavia's model, a **"nearby Mazdoors interested in your job" list inside the job detail/chat view**, not a map you browse before posting. The Bid Comparison Dashboard maps naturally onto the *negotiating* state of a job (multiple Mazdoors chatting/quoting on the same post) — that's a good, low-risk feature to add.
- **Explicitly out of scope for now** (real product decisions the team hasn't made, flagged in §9 as an open question rather than assumed): full map-based discovery, "Hire Now" instant-match, Mazdoor Plus / Mazdoor Pro subscriptions, voice search, achievement-badge gamification, AI job recommendations. These are strong ideas (see §6) but each implies backend work beyond a styling pass.

## 5. Brand identity (per the `brand` skill)

- **Mark:** orange shovel + pickaxe forming a "U", closing in a handshake — reads as *skilled labor + trust*. Use it as a lockup (icon + wordmark) for splash/auth screens, and the icon alone for app icon/favicon/small UI marks.
- **Color:** `packages/shared/src/theme.ts` already encodes a palette that matches the logo's orange closely (`brandOrange #F5680A`) and pairs it with a blue (`brandBlue #1B6FB8`) as a second accent. That blue is **not derived from the logo** — it was a role-accent decision (`roleAccent.mazdoor = orange`, `roleAccent.customer = blue`), a defensible convention (warm = the person doing the work, cool = the person paying/trusting) but worth your explicit sign-off since it's a genuine brand choice, not a mechanical color-extraction. Tier colors (bronze/silver/gold/diamond) and semantic colors (success/warning/danger/info) are already defined.
- **Typography:** Poppins for headings (already wired via `@expo-google-fonts/poppins`), system font for body. This is a reasonable, legible pairing for a utility/trust app; no change proposed.
- **Voice:** the docx's own copy ("PAY NOW", "SOS", direct/plain operational language) plus the PDFs' microcopy style (short, reassuring, safety-forward — "Your number is private", "This worker's CNIC has been verified") sets the tone: plain, confident, safety-and-trust forward, minimal jargon, bilingual-ready (Urdu/English/Punjabi/Pashto/Sindhi per both PDFs).
- **Action:** create `docs/brand-guidelines.md` (the brand skill's source of truth) capturing the above, then run `sync-brand-to-tokens.cjs` so `assets/design-tokens.json/css` and `packages/shared/src/theme.ts` stay in lockstep instead of drifting. This is a Phase 0 task (§7).

## 8. Phased roadmap

**Scope for this engagement's first execution pass (confirmed with you): Phase 0 + Phase 1 below.** Execution order is **mobile-first, admin web second** (founder call, 2026-09-13 — the mobile app is what ships to end users by Dec 20; the admin portal is an internal tool that can trail behind). Phases 2+ are follow-on work, sequenced but not started until you green-light each one.

### Phase 0 — Foundation (design system rollout)
- Write `docs/brand-guidelines.md` as the documented source of truth; keep `packages/shared/src/theme.ts` as the actual typed source both apps import (the generic brand-skill sync script writes a standalone `assets/design-tokens.json/css` pipeline that nothing in this monorepo reads yet, so guidelines↔tokens stays a documented manual sync, not a generated one, until that's worth automating).
- **Mobile (first):** extend the existing theme (spacing scale, radii, shadow/elevation tokens), add `lucide-react-native` as the icon set, and build out the shared component set (buttons, inputs, cards, status pills, empty states, loading skeletons) so every screen pulls from one system instead of ad hoc inline styles like the current `styles.photoTile` one-offs.
- **Admin (second, after mobile Phase 1 is in a reviewable state):** install Tailwind + shadcn/ui, wire `tailwind.config` to the existing `applyCssVariables()` runtime tokens (already the established pattern — Tailwind should read the same `--color-*` custom properties, not re-hardcode hex), convert `Shell.tsx` and one representative module as the template for the rest.

### Phase 1 — Core job loop, full polish
The end-to-end path a real job takes, styled and completed to production quality. **Mobile first, in this order:**
1. **Auth/Onboarding:** phone entry → OTP → role picker → CNIC/KYC upload → pending/verified states, restyled with the PDFs' state handling (wrong-code shake, resend countdown, verification pending/approved/rejected).
2. **Customer flow:** Post a Job (real photo picker, urgency/budget fields) → Job Detail (bid/quote comparison, §6.1) → Chat → Confirmation → Entry PIN display → Live status/tracking → Job in progress → Completion confirm → Pay Now → Rating & review.
3. **Mazdoor flow:** Dashboard/job queue (online-offline toggle, job cards per the Worker PDF's layout) → Job Detail → Accept → Entry PIN entry → Active job/Arrived/In progress → Mark complete → Earnings credited → Withdrawal.
4. **Shared:** Chat, SOS activation/active screens, Settings, verified-badge treatment everywhere a name appears.

**Then admin, once mobile is reviewable:**
5. **CRM:** restyle Jobs table, Verification Kanban, SOS monitor on the new Tailwind/shadcn base; add SLA-age indicators (§6.9).
6. **HRM/Finance:** currently single-paragraph placeholders — build the member directory (HRM) and fund dashboard (Finance) to a first real version per the §9 split (Finance gets full attention now; HRM's attendance tracker/dispatch calendar move to Phase 2).

### Phase 2 — Payments, wallet & disputes depth
Escrow confirmation screen, payment method selection, wallet/add-money, withdrawal + bank account management, Material Quote flow, dispute category picker + detail thread, warranty tab.

### Phase 3 — Profile, settings, notifications
Saved addresses, notification preferences, language settings (5 languages per both PDFs), notification center, help center/FAQ, support tickets.

### Phase 4 — Growth & retention (needs product sign-off first, see §9)
Referral, subscriptions (Mazdoor Plus/Pro), AI recommendations, surge pricing, achievement badges, corporate/B2B portal, in-app translation, recurring subscriptions.

## 9. Decisions (resolved 2026-09-13)

1. **Customer discovery model: keep post-and-negotiate.** It's built, tested, and documented; a live-map/instant-"Hire Now" model is a real v2 differentiator worth doing well later, not a Dec 20 launch blocker. Revisit once the post-and-negotiate flow has real usage data.
2. **Blue stays the customer-role accent.** In a single role-locked app, accent color is the cheapest signal a user has for "which mode am I in right now" — Mazdoor screens read warm/orange, Customer screens read cool/blue. Already wired through the tokens; reversible later at zero structural cost if it ever tests badly.
3. **Icon set: Lucide, on both surfaces.** `lucide-react` for admin (shadcn's own default — zero extra config) and `lucide-react-native` for mobile. One icon vocabulary shared across both surfaces instead of two libraries (e.g. Phosphor + Lucide) drifting apart over time.
4. **HRM/Finance split in Phase 1.** Finance gets real Phase 1 attention (fund dashboard, pay editor scaffold) — real money starts moving at MVP launch and it's already access-gated to Finance Head/CEO in `ARCHITECTURE.md §7`, so a placeholder here is a live risk, not a cosmetic gap. HRM gets a functional member directory only in Phase 1; the attendance tracker and drag-and-drop dispatch calendar move to Phase 2, since HRM has no external user until Ustavia has salaried staff to manage.

- **2026-09-13 — Ran both apps locally for the first time (admin via `vite dev`, mobile via `expo start --web`) and found two real bugs that typecheck/lint/build could never catch, since neither exercises actual runtime rendering:**
  1. **Admin rendered a blank white screen.** Root cause: `apps/admin` had its own duplicate copy of React (its `package.json` wanted `^19.2.8`, incompatible with the exact `19.2.3` `apps/mobile` pins and that npm had hoisted to the workspace root), so admin's own component tree and the Radix primitives it imports (`Tabs`, `Dialog`) were running against two different React instances — the classic "Invalid hook call" crash.
